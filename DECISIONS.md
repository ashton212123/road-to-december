## Home was actually slow — real bug, found and fixed

You reported Home just sitting there loading. Root-caused it to two real, compounding issues (not vague "slowness," specific bugs):

1. **`getCanvasSummary()` triggers a live Canvas API call whenever its 20-minute cache is stale**, and since your Canvas token has never successfully authenticated, the cache has stayed empty this whole time — meaning *every single Home load* was making a real network call to Canvas that always ended in a 401, forever, with no way to ever cache past it. Home also called it **twice** (once directly, once again inside `evaluateAlerts()`), which could race two live syncs against the same cache rows concurrently. Fixed: `getCanvasSummary()` now takes a `{ sync: boolean }` option; Home reads cache-only (`sync: false`, fast DB read, no external call) and shares that one read with `evaluateAlerts()` instead of fetching twice. The School page keeps live-syncing (it has its own "Sync now" button and a human there is expecting to wait a moment).
2. **`evaluateAlerts()` — the "Coach" alert logic — ran ~8 database queries sequentially** (`await` one at a time) instead of in parallel, and one of them (`getWorkoutLogsSince(today)`) was called **twice inside a loop with identical arguments**, pure waste. Rewrote it to fetch everything it needs in one `Promise.all` up front. Measured directly: 776ms → 140ms for the pattern Home actually uses (pre-fetched Canvas summary), same alert output both before and after (verified identical, so this was a pure perf fix, not a behavior change).

Neither of these was something I could have caught by reading code casually — both needed actually tracing the request path and measuring. Worth remembering: any time a page feels slow, check for (a) an external API call sitting in the render path and (b) sequential `await`s that could be a `Promise.all` instead — those two patterns caused this.
