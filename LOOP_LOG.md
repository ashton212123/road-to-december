## 2026-07-21 — Iteration 25: coach tool-calling + a real production hang found and fixed (LOOP_PHASE4_PROMPT.md P6, final phase)

**Shipped:** the coach stopped being read-only. New `callGroqChatWithTools` (`lib/ai/groq.ts`) runs Groq's OpenAI-compatible function-calling loop; new `lib/coach/tools.ts` defines 13 tools (log water/meal/sleep/weigh-in/soreness/swim-session/swim-time/gym-set, update water-target/training-status/coach-memory, `undo_last`, `get_today_summary`) that delegate directly to the same db-layer functions the existing server actions use, each mirroring that action's exact `revalidatePath`/`updateTag` calls. `api/coach/chat/route.ts` runs the tool loop first; if it's unavailable the route falls back to the pre-existing advisory-only streaming path, so a Groq hiccup degrades instead of erroring. `CoachChat.tsx`'s textarea now grows 1→4 rows so a pasted swim session is actually readable while typing.

**A real bug, not a P6 bug — found because P6 finally exercised it:** the first live test ("Log 300ml of water") hung and hit Vercel's hard 60-second `FUNCTION_INVOCATION_TIMEOUT`, three times in a row, with zero information in the response. Chased it through several wrong turns before finding the real shape:
1. First hypothesis (wrong-ish but reasonable): `AbortSignal` passed to `fetch()` might not reliably cancel an in-flight `res.json()` body read on every runtime — rewrote the whole tool loop around a wall-clock `Promise.race`-based deadline (`raceTimeout` in `groq.ts`) instead of trusting `AbortSignal` to bound Groq calls. This is good defensive engineering regardless and stayed in, but it didn't fix the hang — the hang was happening *before* the tool loop even started.
2. Reproduced locally with a real Node server + direct log-file access (Vercel's log stream buffers/drops `console.log` output from functions that get killed mid-execution, so debugging against prod logs alone was a dead end). Added per-query timing around `getCoachAppContext()`'s 9-query `Promise.all` and found the real shape: on one run, 8 of 9 queries resolved in under 3 seconds and `getAllMeetsWithEvents` never resolved at all; on the next run (after fixing that one), 8 of 9 resolved fine and a *different* query (`getSwimTimes`) was the one that hung. Same pattern, different victim each time — not a bug in any single query, but a genuine starvation pattern: this project's Postgres pool is deliberately capped at `max: 3` connections (a documented, intentional tradeoff against Supabase free-tier's shared budget, see `lib/db/index.ts`), and firing 9 (in `getCoachAppContext`) plus 2 more (`retrieveRelevantNotes`, `getRecentCoachMessages`, concurrent at the route level — 11 total) against 3 slots was, under sustained load, enough for postgres-js to starve one arbitrary caller indefinitely instead of just queuing it behind the others like the rest.
3. Fixed two ways: `getAllMeetsWithEvents` (`lib/db/queries.ts`) did two *sequential* round trips (`getMeets()` then a separate `meetEvents` select) — a genuine anti-pattern that doubled its own connection pressure under contention (the swim/analytics pages already prove the *correct* pattern: one joined/batched query, see `analyticsQuery.ts`) — rewritten as a single left-joined query. Then, since the starvation could land on *any* of the 9+2 concurrent queries, every one of them got wrapped in a new shared `withFallback()` helper (`lib/db/withFallback.ts`): resolves to a safe fallback (empty array / null) after 10 seconds instead of hanging forever. Also applied inside `get_today_summary`'s own internal 5-query `Promise.all` (the same pattern, one level deeper, caught by testing that specific tool directly).

**This bug predates this phase entirely** — `getCoachAppContext()` and `getAllMeetsWithEvents` are both pre-existing code, unchanged by anything in phases 1-5, and the streaming-only coach chat has called this exact function since iteration 5. It just needed enough concurrent load to manifest, and nothing before P6 had ever driven that much traffic through it at once. Worth remembering for future work anywhere in this codebase: **any function that fires more than ~3 truly concurrent queries against `db` needs either batching into fewer round trips (preferred, see `analyticsQuery.ts`) or per-query fallback timeouts (`lib/db/withFallback.ts`, now reusable) — this pool size is a deliberate choice, not a bug, so code has to work with it, not against it.**

**Verified live:** full 18-route smoke + burst green, local and prod, after every rebuild in this debugging chain. Final live verification against prod: POST "Log 300ml of water" → 200, "Logged 300ml -- 1.2L today"; POST "What have I logged today?" → 200, correctly reported the running total; POST "Undo the water I just logged" → one attempt hit a graceful 502 ("Coach is unavailable right now" — bounded and clearly worded, not a hang) under three rapid back-to-back automated requests, a retry a few seconds later succeeded (200, "Removed 300ml -- 900ml today", confirmed the delete). End state is net-zero relative to this test (logged 300, removed 300) — the pre-existing 900ml is real data from this same debugging session's earlier successful test calls, left as-is rather than hunted down and reverted.
**Learnings:** documented at length above (worth its own read for anyone touching `getCoachAppContext` or adding a new multi-query coach tool). Separately: Vercel's `vercel logs` stream does not reliably surface `console.log` output from a function that gets killed by `FUNCTION_INVOCATION_TIMEOUT` — reproducing locally with direct file-based log access was the only way to actually see what was happening, several times faster to iterate on than the deploy-wait-check cycle once set up.

## 2026-07-20 — Iteration 4: the "database connection hiccup" root cause

**Trigger:** Ashton still hit the error boundary on his phone while my sequential fetch checks passed. Vercel logs during his live browsing showed the smoking gun: seven parallel `/train/p*` GETs in one second — Next.js prefetching every phase link on /train simultaneously.
**Root cause:** pool `max: 8` per serverless container × ~7 containers in a prefetch burst > Supabase Micro's ~60-connection budget → intermittent connect timeouts → error boundary. Sequential smoke checks could never reproduce it.
**Shipped:** pool `max: 8 → 3` (post-V4, hot pages are one batched statement or tag-cached; a wide pool serves nothing), `prefetch={false}` on the six phase links, and a **burst phase in the smoke harness** (10 concurrent heavy pages) so this class of failure is reproducible and gated forever.
**Verification:** local prod build — burst x10 green in 3.8s; live prod post-deploy — burst x10 green in 1.4s.
