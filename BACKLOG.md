- [ ] `withRetry` (`lib/db/withRetry.ts`) races each DB call against a timeout via `Promise.race` but never cancels the losing side — a timed-out attempt's query keeps running and holding a pool connection, and each of its 3 retries fires more queries at the same already-tiny 3-connection pool, snowballing one slow request into an extended outage under sustained/bursty load (found while shipping loop 38, see LOOP_LOG.md). Fix would be passing an `AbortSignal` through to the underlying `postgres` query so a timeout actually releases the connection. Not urgent (same accepted Micro-tier tradeoff as everything else in this class) but a real correctness gap in the mitigation itself, not just capacity.
